# Reticulum Airtime Design

## Goal

Minimize Reticulum airtime while showing that Codrik is generating a reply. If
a Reticulum-routed work item remains active for five seconds after its first
model step starts, Codrik sends one plain-text `Думаю...` message. The final
answer remains a separate LXMF message limited to 500 Unicode characters.

## Scope

- Applies only to linked Reticulum conversations that create agent work.
- Starts the delay on `ModelStepStarted`.
- Sends at most one `Думаю...` message per work item.
- Suppresses the message when the work item completes, fails, or is cancelled
  before five seconds.
- Does not stream text deltas, report tool names, edit messages, send repeated
  status updates, or define custom LXMF fields.
- Applies a Reticulum-only brevity instruction to every model step in the work
  item, including model steps after tool execution.
- Limits final assistant text to 500 Unicode characters. Tool calls and tool
  observations are not truncated.

## Approach

Add a small Reticulum activity worker beside the existing Reticulum ingress and
delivery loop. It subscribes to the existing `GatewayActivityHub`, filters for
the configured `reticulum:<destination>` gateway, and tracks active work items
with their durable delivery routes.

The existing runtime event publisher must publish gateway activity when either
Telegram or Reticulum is configured. Reticulum composition passes the shared
activity hub to the new worker.

At model-request construction, the actor runner inspects the attached durable
delivery route. For a `reticulum:` route it appends a transient system
instruction requiring a direct answer of at most 500 Unicode characters. The
instruction is injected into every model request for that work item but is not
checkpointed or added to conversation memory. Other routes keep existing
prompts unchanged.

## Flow

1. `ModelStepStarted` creates or updates state for the work item and sets a
   five-second deadline.
2. A bounded maintenance timer checks due states.
3. If the work item is still active at the deadline and no status was sent, the
   worker enqueues `Думаю...` through the existing gateway delivery store.
4. `Completed`, `Failed`, or `Cancelled` removes the state. A terminal event
   racing the timer wins whenever it is observed before enqueueing.
5. The normal outbox path independently creates and delivers the final answer.

Additional model steps for the same work item do not create additional status
messages. `TextDelta`, descriptions, and tool activity do not change the timer.

## Delivery Semantics

The status uses the work item's existing Reticulum route and a deterministic
idempotency key derived from the local destination and work item ID. It is a
standalone delivery, not agent output and not conversation memory.

The status is best effort with one delivery attempt. A retryable, terminal, or
unknown outcome becomes terminal for this status message; it is never retried.
This prevents a cosmetic update from repeatedly consuming Reticulum airtime or
remaining ahead of the final answer. Failure to enqueue or deliver the status
is logged and does not fail the Reticulum component or actor run.

The final response keeps its existing durable delivery and retry behavior.

## Response Limit

The model instruction is the primary limiter because semantic compression is
better than transport truncation. Before finalization, Codrik counts Unicode
characters in Reticulum-routed assistant text. Text at or below 500 characters
is unchanged.

If the model exceeds the limit, Codrik keeps the longest prefix ending at a
sentence boundary within 497 characters and appends `...`. If no sentence
boundary exists, it keeps the first 497 characters and appends `...`. The
bounded text is what gets checkpointed as the assistant response and delivered,
so conversation memory matches what the user received. UTF-8 is never cut at a
byte boundary.

The limit applies only when finalizing plain assistant text. It must not alter
tool-call arguments, tool results, linking responses, errors generated by the
gateway, or replies through CLI and Telegram.

## Lifecycle

The worker runs as a separately supervised Reticulum activity component. It
exits cleanly on shutdown or a closed activity channel. Lagged broadcast events
are tolerated; missing a cosmetic status is preferable to reconstructing stale
activity.

State is in memory only. Restarting Codrik drops pending timers; no recovery is
needed because the status is informational.

## Testing

Focused Tokio tests verify:

- no status before five seconds;
- one `Думаю...` delivery after five seconds;
- completion, failure, or cancellation before the deadline suppresses it;
- repeated model steps still enqueue once;
- Telegram and unrelated Reticulum routes are ignored;
- status enqueue/delivery failure does not affect the final response path;
- runtime composition publishes activity when Reticulum is configured without
  Telegram;
- every Reticulum model request receives the transient brevity instruction;
- CLI and Telegram model requests remain unchanged;
- responses of 500 characters are unchanged;
- longer Unicode responses are shortened to at most 500 characters without
  splitting a code point, preferring a sentence boundary;
- the shortened response is both checkpointed and delivered.

Existing Reticulum bridge, ingress, delivery, and full runtime tests remain
green.
